## 1. Enforced Guards (Reference)

Per-call preconditions. Heading IDs below (`G-N`) are anchor targets from x-ray.md attack surfaces.

#### G-1

`if (accountOf[msg.sender] != 0) revert AlreadyHasAccount()` · `AmplopEnvelopes.sol:536` · One account per address, so `accountOf` stays a function owner → id (R1).

#### G-2

`if (id == 0) revert NoAccount()` · `AmplopEnvelopes.sol:1101` · `_caller()` makes the current owner the only student identity for every student write (PRD invariant 5).

#### G-3

`if (accountId == 0 || accountId > accountCount) revert AccountNotFound(accountId)` · `AmplopEnvelopes.sol:1106` · Stops writes into uninitialised account slots (owner 0).

#### G-4

`if (msg.sender != cardService) revert NotCardService()` · `AmplopEnvelopes.sol:1111` · R3 trust boundary for authorize / collect / refund.

#### G-5

`if (acc.trusted == address(0) || msg.sender != acc.trusted) revert NotTrusted()` · `AmplopEnvelopes.sol:1115` · Only the linked trusted person approves Emergency and recovery; zero-check blocks `address(0)` callers.

#### G-6

`if (msg.sender != treasury) revert NotTreasury()` · `AmplopEnvelopes.sol:793` · R3: the only way value enters accounts besides refunds.

#### G-7

`if (paymentUsed[paymentId]) revert PaymentAlreadyUsed(paymentId)` · `AmplopEnvelopes.sol:798` · Single-use rupiah payment ids; prevents double crediting.

#### G-8

`if (purchaseUsed[purchaseId]) revert PurchaseIdUsed(purchaseId)` · `AmplopEnvelopes.sol:845` · A purchase id (approved or declined) is never re-authorised, so a purchase record is never overwritten.

#### G-9

`if (_available(acc, pay) < amount)` / `if (pay == EVERYDAY || _available(acc, EVERYDAY) < amount)` · `AmplopEnvelopes.sol:857-859` · Holds never push an envelope below zero; only Everyday steps in (R10, PRD invariant 3).

#### G-10

`if (p.state != PurchaseState.Held) revert NotHeld()` · `AmplopEnvelopes.sol:890` · Collect only from a live hold; one collect per purchase.

#### G-11

`if (amount > h) revert AmountAboveHeld()` · `AmplopEnvelopes.sol:893` · Settlement can never receive more than was held.

#### G-12

`if (_clock(acc) >= p.createdAt + HOLD_PERIOD) revert HoldExpired()` · `AmplopEnvelopes.sol:895` · Card service loses the hold after 7 account-clock days (R13).

#### G-13

`if (p.state != PurchaseState.Held) revert NotHeld()` · `AmplopEnvelopes.sol:912` · Release only a live hold; prevents double return.

#### G-14

`if (msg.sender != cardService && _clock(acc) < p.createdAt + HOLD_PERIOD) revert HoldNotExpired()` · `AmplopEnvelopes.sol:914` · Anyone may free a stale hold; before that only the card service.

#### G-15

`if (p.state != PurchaseState.Collected && p.state != PurchaseState.Refunded) revert NotCollected()` · `AmplopEnvelopes.sol:930` · Refunds only after money actually left.

#### G-16

`if (uint256(p.refunded) + amount > p.collected) revert RefundTooLarge()` · `AmplopEnvelopes.sol:932` · Refunds never exceed what went to settlement.

#### G-17

`if (p.accountId != id) revert NotOwner()` · `AmplopEnvelopes.sol:595` · A student moves only their own purchases.

#### G-18

`if (p.moved) revert AlreadyMoved()` / `if (p.envelope != EVERYDAY) revert NotFromEveryday()` · `AmplopEnvelopes.sol:597-598` · R15: one move, only out of Everyday.

#### G-19

`if (_clock(acc) >= p.createdAt + MOVE_PERIOD) revert MovePeriodOver()` · `AmplopEnvelopes.sol:599` · R15 seven-day window on the account clock.

#### G-20

`if (_available(acc, t) < m) revert TargetShort()` · `AmplopEnvelopes.sol:605` · The target envelope must be able to pay, so no envelope goes negative.

#### G-21

`if (acc.em.status == EmergencyStatus.Open) revert RequestAlreadyOpen()` / `if (acc.pendings[LockOff].active) revert LockOffPending()` · `AmplopEnvelopes.sol:624-625` · One open request at a time, never during a lock-off.

#### G-22

`if (amount > acc.locked) revert AmountAboveLocked()` · `AmplopEnvelopes.sol:627` · An open request is always coverable by `locked` (feeds I-5).

#### G-23

`if (acc.em.status != EmergencyStatus.Open) revert NoOpenRequest()` · `AmplopEnvelopes.sol:645,712,753` · Cancel / approve / finalize only an open request.

#### G-24

`if (_clock(acc) < acc.em.opensAt) revert WaitNotOver(acc.em.opensAt)` · `AmplopEnvelopes.sol:754` · R17 48-hour wait before Emergency opens without approval.

#### G-25

`if (!acc.lockOn) revert LockAlreadyOff()` / `if (acc.em.status == EmergencyStatus.Open) revert RequestAlreadyOpen()` · `AmplopEnvelopes.sol:653-654` · Lock-off never races an open request (feeds I-5, I-6).

#### G-26

`if (!p.active || (kind == Split && now_ >= p.readyAt)) revert NothingPending()` / `if (now_ >= p.readyAt) revert WaitOver()` · `AmplopEnvelopes.sol:665-666` · R24: cancel only during the wait.

#### G-27

`if (!p.active) revert NothingPending()` / `if (_clock(acc) < p.readyAt) revert WaitNotOver(p.readyAt)` · `AmplopEnvelopes.sol:1208-1209` · Every "finish" of a pending change waits the full 48 hours.

#### G-28

`inv.key == 0 / inv.used / expiry / signer != inv.key / msg.sender == owner / trustedAccountOf[msg.sender] != 0 / acc.trusted != 0` · `AmplopEnvelopes.sol:691-699` · Invite is single-use, time-boxed, bound to the caller by EIP-712, and keeps trusted ≠ owner and one account per trusted person.

#### G-29

`accountOf[newOwner] != 0 / newOwner == acc.trusted / TrustedRemoval active / recoveryAccountOf busy` · `AmplopEnvelopes.sol:723-727` (re-checked `776-777`) · Recovery target must be a fresh, non-trusted address not claimed by another account.

#### G-30

`if (token.balanceOf(address(this)) - before != amount) revert TransferMismatch()` · `AmplopEnvelopes.sol:1224` · Fee-on-transfer or odd tokens cannot desync PRD invariant 1 on deposit / refund pulls.

## 2. Inferred Invariants (Single-Contract)

Derivation methods: Δ-pair, guard lift, state-machine edge, temporal predicate, NatSpec / spec-stated. Categories: `Conservation` · `Bound` · `Ratio` · `StateMachine` · `Temporal`.

---

#### I-1

`Conservation` · On-chain: **Yes**

> For every account and envelope e: `held[e] == Σ p.held` over that account's purchases with `envelope == e`.

**Derivation** — Δ-pair: `authorize` `acc.held[pay] += amount` (867) ↔ `p.held = amount` (877); `collect` `acc.held -= h` (898) ↔ `p.held = 0` (900); `releaseHold` 917 ↔ 919; `movePurchase` moves `held[EVERYDAY] → held[t]` (608-609) ↔ `p.envelope = t` (613). No other writer of either.

**If violated** — PRD invariant 1 drifts; collect/release underflow-reverts or leaves stranded held balance.

**Test** — `invariant_XR_heldMatchesHeldPurchases`

---

#### I-2

`Bound` · On-chain: **Yes**

> For every purchase: `refunded <= collected <= amount`.

**Derivation** — guard-lift: G-11 (`amount > h`, 893) and G-16 (`refunded + amount > collected`, 932). Write sites: `collected` only at 901, `refunded` only at 934; `held` set to `amount` only at 877.

**If violated** — settlement refunds or collects more than the student paid.

**Test** — `invariant_XR_purchaseRecordConsistent`

---

#### I-3

`StateMachine` · On-chain: **Yes**

> Purchase state: `None → Held` (authorize) `→ Collected → Refunded*` or `Held → Released`. `Held ⇔ held == amount && collected == 0`; every other state has `held == 0`; `Released ⇒ collected == 0`; `Collected ⇒ refunded == 0`.

**Derivation** — edge: `Held@873`; `Held@890 → Collected@902`; `Held@912 → Released@920`; `{Collected,Refunded}@930 → Refunded@935`. No write sets `Held` except 873 behind G-8, so no reverse path.

**If violated** — a released or collected purchase could be collected / released again (double spend).

**Test** — `invariant_XR_purchaseRecordConsistent`

---

#### I-4

`StateMachine` · On-chain: **Yes**

> `moved` is a one-shot latch, and a moved purchase pays from Food, Transport or Study.

**Derivation** — edge: `require(!p.moved)@597 → p.moved = true@614`; `uint8(to) >= EVERYDAY` revert at 596 before `p.envelope = t` at 613. No writer resets `moved`.

**If violated** — the same purchase could shift money between envelopes repeatedly.

**Test** — `invariant_XR_purchaseRecordConsistent`

---

#### I-5

`Bound` · On-chain: **Yes**

> While a request is `Open`: `0 < em.amount <= locked`, and `em.requestSeq == requestSeq`.

**Derivation** — guard-lift: G-22 (627) + amount zero check (626). Write sites of `locked`: `+=` at 820 (only grows), `-=` at 1195 (sets status `Opened` in the same body, 1197), `= 0` at 764 (only after LockOff pending, which G-21/G-25 make exclusive with `Open`). `em` written only at 631 and status at 646/1197.

**If violated** — `_openEmergency` underflow-reverts; request can only be cancelled.

**Test** — `invariant_XR_openEmergencyWithinLocked`

---

#### I-6

`StateMachine` · On-chain: **Yes**

> An `Open` Emergency request and a pending LockOff never coexist.

**Derivation** — guard-lift: `requestEmergency` blocks on LockOff active (625); `startLockOff` blocks on `Open` (654). These are the only writers of `em.status = Open` (631) and `pendings[LockOff].active = true` (1203 via 655).

**If violated** — lock-off could zero `locked` under an open request (I-5 broken).

**Test** — `invariant_XR_openEmergencyWithinLocked`

---

#### I-7

`StateMachine` · On-chain: **Yes**

> `lockOn` is a one-way latch `true → false`; once off, `locked == 0` forever; a pending LockOff implies `lockOn`.

**Derivation** — edge: `true@542 → false@766` (with `locked = 0` at 764). `deposit` adds to `locked` only when `lockOn` (820). `startLockOff` requires `lockOn` (653). No writer sets `lockOn = true` after `register`.

**If violated** — Emergency money would sit in `locked` with no path out except R17 (PRD invariant 2 path).

**Test** — `invariant_XR_lockOffMeansNothingLocked`

---

#### I-8

`Bound` · On-chain: **Yes**

> `accountOf` and `acc.owner` are mutually inverse: `accountOf[owner(id)] == id` and `accountOf[x] == id ≠ 0 ⇒ owner(id) == x`; owner ≠ 0.

**Derivation** — guard-lift: G-1 (536) and G-29 / 776. Write sites of `accountOf`: 543 (register), 779-780 (finishRecovery). Write sites of `owner`: 540, 781. Each pair updated together.

**If violated** — two addresses act as the same student, or an old key keeps access after recovery.

**Test** — `invariant_XR_ownerAndTrustedMapsOneToOne`

---

#### I-9

`Bound` · On-chain: **Yes**

> `trustedAccountOf` and `acc.trusted` are mutually inverse, and `owner != trusted` for every account.

**Derivation** — guard-lift: G-28 (697-699) and G-29 (724, 777). Write sites of `trusted` / `trustedAccountOf`: 702-703 (acceptInvite), 744-745 (finishRemoveTrusted). `owner` changes only at 781, behind `newOwner == acc.trusted` (777).

**If violated** — a student could approve their own Emergency or recovery.

**Test** — `invariant_XR_ownerAndTrustedMapsOneToOne`

---

#### I-10

`Bound` · On-chain: **Yes**

> `recoveryAccountOf[x] == id ≠ 0 ⇔ pendings[Recovery]` of `id` is active with target `x`.

**Derivation** — guard-lift: busy check (726-727). Write sites of `recoveryAccountOf`: 730 + 732 (approveRecovery clears old target, sets new), 667 (cancelPending), 782 (finishRecovery). Pending Recovery writes: 731, 668, 775.

**If violated** — a stale entry blocks another account's recovery to that address (`RecoveryTargetBusy`).

**Test** — `invariant_XR_recoveryMapMatchesPending`

---

#### I-11

`Bound` · On-chain: **No**

> While a Recovery is pending, its target owns no account (`accountOf[target] == 0`), so `finishRecovery` can succeed.

**Derivation** — guard-lift: `if (accountOf[newOwner] != 0) revert NewOwnerHasAccount()` at 723 (re-checked 776). Write sites of `accountOf`: **543 (`register`) has no check against `recoveryAccountOf`** — unguarded; 780 guarded.

**If violated** — after the wait, `finishRecovery` reverts at 776 and `cancelPending` reverts `WaitOver` at 666, so the pending Recovery cannot be cleared by the student; `removeTrusted` then reverts `RecoveryPending` at 583. Only a new `approveRecovery` by the trusted person clears it.

**Test** — `invariant_XR_recoveryTargetStaysFree` (**fails**; shrunk sequence: `approveRecovery` → `register` by the target).

---

#### I-12

`Bound` · On-chain: **Yes**

> The effective split and any pending split are five multiples of 5 summing to 100.

**Derivation** — guard-lift: `_checkSplit` (1228-1235). Write sites of `split`: 541 (after check, 537), 557 (after check, 552), 1217 (unpacks `p.data` written only at 564 after the check). Pack/unpack round-trip is exact for values ≤ 100.

**If violated** — R4 parts would not sum to the deposit; PRD invariant 1 would drift.

**Test** — `invariant_XR_splitAlwaysValid`

---

#### I-13

`Bound` · On-chain: **Yes**

> At most three live schedule records per account (`scheduleCount <= 3`), with distinct `startMonday`s, none in the future.

**Derivation** — guard-lift: `_scheduleFor` matches existing `startMonday` (1176) before appending; `_fold` (1155-1171) removes every record with `sharesOut == 4` before each append (803). `n == MAX_SCHEDULES` (1178) is unreachable. Account clock is monotonic (I-15), so `startMonday <= monday`.

**If violated** — `deposit` could hit `TooManySchedules` (DoS), or `_sharesOut` underflow.

**Test** — `invariant_XR_scheduleCountAtMostThree` (existing) + `invariant_XR_scheduleRecordsWellFormed`

---

#### I-14

`Ratio` · On-chain: **Yes**

> For each live record and envelope: `4 * base[e] <= part[e]`; released = `k * base[e]` for `k < 4`, `part[e]` at `k = 4` (leftover units land on the fourth Monday).

**Derivation** — Δ-pair: `r.base[e] += parts[e] / 4` (825) ↔ `r.part[e] += parts[e]` (826), same loop body; `Σ floor(p_i/4) * 4 <= Σ p_i`. Read in `_live` (1145).

**If violated** — released amount could exceed the part, making `available` larger than deposited.

**Test** — `invariant_XR_scheduleRecordsWellFormed`

---

#### I-15

`Temporal` · On-chain: **Yes**

> Account clock = `block.timestamp + skipSeconds`, `skipSeconds` is a whole number of days and only grows (so the clock is monotonic).

**Derivation** — temporal: `_clock` (1120); only writer of `skipSeconds` is `skipDays` (678-679), `+= numDays * 1 days` with `numDays ∈ [1,14]` (677), gated by immutable `demoMode` (675).

**If violated** — waits could be shortened or `_sharesOut` could underflow.

**Test** — `invariant_XR_accountClockIsBlockTimePlusSkips`

## 4. Economic Invariants

---

#### E-1

On-chain: **Yes**

> The contract is always solvent per account: every unit a student can see (available, unreleased, held, locked) is backed 1:1 by tokens held, and no flow lets an account spend more than deposits + refunds − collections.

**Follows from** — `I-1` + `I-2` + `I-5` + `I-7` + `I-14` + `I-16`

**If violated** — one student's spending would be paid from another student's balance.
