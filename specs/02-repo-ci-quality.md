# 02. Repository, CI and quality gates

Status: Ready · Source: PRD sections 6, 13, 14, 15, 16 · Depends on: 01

## Goal

One repository that is always deployable. Every push runs every gate in PRD 15 "Gates on every push". Production deploys only from a commit where all gates are green. Every commit, by a person or an AI agent, follows the PRD 15 commit rule.

## In scope

- npm workspaces, Node 22, `packages/shared` skeleton and its generated files.
- TypeScript, ESLint, Prettier, solhint and `forge fmt` configuration. Zero errors, zero warnings.
- Git hooks: pre-commit (lint-staged and gitleaks), commit-msg, pre-push.
- Commit rules, branch and repository settings.
- GitHub Actions: one workflow that runs every PRD 15 gate, plus Dependabot and the production deploy job.
- Foundry test profiles and the coverage floors.
- `.gitignore`, `.env.example`, `LICENSE`, `CLAUDE.md`, `.monskills`.
- Dependency policy and the checks that enforce it.
- Pinned AI skills (MONSKILLS and pashov/skills).

## Out of scope

- The tests themselves. Contract tests are 03, server tests are 05 and each feature spec, indexer tests are 16, the end-to-end harness and case map are 19.
- The list of key patterns the bundle scan looks for (05 owns it; this spec runs it).
- Deploy scripts and the self-audit report (04).
- Content of README, SECURITY.md and the docs site (18).

**S02-11. Commit rule.** This text is copied unchanged into `CONTRIBUTING.md` and `CLAUDE.md` (S02-28):

> Never one big commit. Commit after each finished piece (a feature plus its tests), about every 30–90 minutes, and push at least once a day. Never squash the history or force-push `main`. Messages follow `type(area): what changed`, for example `feat(card): decline gambling purchases`. Self-audit fixes name their finding: `fix(contract): cap skipDays (SA-03)`. Every commit passes the pre-commit hook, so `main` is always deployable. The same rule applies when an AI agent makes the commits.

The commit-msg hook and the CI job `commits` enforce the message shape:

```
^(feat|fix|test|docs|chore|refactor|ci|build|perf|style|revert)\([a-z0-9-]+\): [^\s].{0,98}( \(SA-\d{2}\))?$
```

- `area` is a lowercase word naming the folder or job: for example `contract`, `card`, `topup`, `indexer`, `landing`, `docs`, `ci`, `e2e`.
- A commit that fixes a self-audit finding (04) must end with ` (SA-xx)`, using the finding id from `audits/2026-10-self-review.md`.
- Merge commits created by GitHub (`Merge pull request …`) are allowed by the CI check.
- No one passes `--no-verify`. `CLAUDE.md` says so to agents.

**S02-12. Repository settings.** Set on GitHub on setup day and recorded as a checklist in `CONTRIBUTING.md`:

- A ruleset on `main`: block force pushes, block deletion. Direct pushes by the owner are allowed (solo builder).
- Merge options: merge commits only. Squash merging and rebase merging are turned off.
- Private vulnerability reporting: on (SECURITY.md, spec 18, points to it).
- Dependabot alerts and Dependabot security updates: on. Secret scanning and push protection: on.
- Code scanning: CodeQL "advanced setup" (the workflow file below), default setup off.
- Actions permissions: "Read repository contents" by default; jobs ask for more only where listed.

**S02-17. Code scanning.**

- CodeQL runs as job `codeql` (S02-13) with `permissions: security-events: write`.
- Semgrep runs from the `semgrep/semgrep` container image pinned by digest: `semgrep scan --config p/default --config p/typescript --config p/react --config p/nextjs --config p/secrets --config p/smart-contracts --severity ERROR --severity WARNING --error --sarif --output semgrep.sarif`, then uploads the SARIF with `github/codeql-action/upload-sarif`. ERROR counts as high and WARNING as medium.
- A false positive is silenced only inline, `// nosemgrep: <rule-id> -- <reason>`. A reason is required; `scripts/check-nosemgrep.mjs` (part of `static`) fails on a `nosemgrep` without `--` and text after it.
- `code-scanning-gate` calls `GET /repos/{owner}/{repo}/code-scanning/alerts?ref=<ref>&state=open` with the job token (`security-events: read`) and fails if any alert has `rule.security_severity_level` in `critical`, `high`, `medium`, or (for tools without security severity) `rule.severity` `error` or `warning`.

**S02-18. Secrets.** `.gitleaks.toml`:

- `[extend] useDefault = true`.
- Extra rule `evm-private-key`: a 64-hex-character value (with or without `0x`) assigned to a name containing `PRIVATE_KEY`, `PRIV`, `SECRET` or `MNEMONIC`, in any file.
- Extra rule `midtrans-server-key`: `SB-Mid-server-` or `Mid-server-` followed by key characters.
- Allowlist: the ten well-known public Anvil default private keys (test only, listed by value with a comment), the fake value pattern used in `.env.example` (`0x` followed by `11` repeated 32 times), and `specs/design/**`.

`secrets` scans the whole history on every push. GitHub secret scanning with push protection is also on (S02-12).

**S02-19. Dependencies gate.** Job `deps`:

1. `npm audit --omit=dev --audit-level=high`. Exit non-zero on any high or critical.
2. OSV-Scanner (exact version) on `package-lock.json`, JSON output. `scripts/check-osv.mjs` fails on any vulnerability with severity HIGH or CRITICAL (GHSA severity, or CVSS v3 score 7.0 or more). Lower ones are printed.
3. Dependabot alerts: `GET /repos/{owner}/{repo}/dependabot/alerts?state=open&severity=high,critical` with the secret `DEPENDABOT_READ_TOKEN` (fine-grained token, this repository only, "Dependabot alerts: read"). Fails if the list is not empty, and fails if the secret is missing (never skipped).
4. `npm run check:deps` (S02-25).

`.github/dependabot.yml`: ecosystems `npm` (directory `/`) and `github-actions` (directory `/`), daily, `open-pull-requests-limit: 5`, group `next` + `react` + `react-dom` patch updates into one pull request. No Dependabot pull request is merged after the 18:00 13 Oct freeze.

**S02-20. Build and bundle scan.** Job `build`:

1. Sets the CI build environment: every `NEXT_PUBLIC_*` name from 01 §7 with test values, and every server-only name from 01 §7 set to a unique canary string (`CANARY_<NAME>_7f3a…`, 24 random hex characters generated in the job).
2. `npm run build` (includes `next build` for `apps/web` and `astro build` for `apps/docs`).
3. `npm run scan:bundle` runs `scripts/scan-bundle.mjs` over every file in `apps/web/.next/static/**` and every prerendered HTML file in `apps/web/.next/server/app/**/*.html`. It fails if it finds:
   - any pattern in 05's pattern file `apps/web/scripts/bundle-scan.patterns.json` (S05-53), which names the server-only variables of 01 §7;
   - any canary value from step 1 (05's exact-value check, S05-54).
     `npm run scan:bundle` runs 05's script `apps/web/scripts/bundle-scan.mjs`; this spec only supplies the canary environment. It prints the file and offset of each hit, and the count of files scanned (a count of 0 is a failure).
4. Runs 17's Lighthouse budget check on the built app (`next start` on the runner).

- `e2e-tier1` runs on every push. It runs 19's `npm run e2e:tier1:ci`: a production build of this commit (`next build` and `next start`, `NODE_ENV=production`) against Anvil with the real contract in demo mode, mock AUSD, Postgres, the Midtrans stand-in and the indexer, in Chromium and WebKit. The job needs Docker (available on the runner). It uploads `playwright-report/` and server logs as artifacts on failure.
- `preview-smoke` runs on every push. It polls `GET /repos/{owner}/{repo}/deployments?sha=<sha>&environment=Preview` and its statuses until Vercel reports `success` (timeout 15 minutes, 10 s between polls), then runs `npm run e2e:smoke` with `BASE_URL` set to the preview URL and the header `x-vercel-protection-bypass: ${{ secrets.VERCEL_AUTOMATION_BYPASS_SECRET }}`. The smoke set (19) sends no transactions.
- Tier 1 against Monad testnet is a separate manual workflow, `.github/workflows/e2e-testnet.yml` (`workflow_dispatch` with input `base_url`), defined by 19. 20 runs it before recording and at the final gate run.

**S02-22. Production deploys only from green commits.**

- Vercel has two projects linked to this repository: `amplop-web` (root `apps/web`) and `amplop-docs` (root `apps/docs`).
- In both projects the Production Branch is set to `vercel-production`, a branch that is never created. Every push, including to `main`, therefore makes only a Preview deployment.
- Job `deploy-production` runs only for `push` to `main`, or `workflow_dispatch` on `main` (used after a Vercel environment change, such as a new indexer URL), and only after `all-green`. It runs `npx vercel@<exact> deploy --prod --yes --token ${{ secrets.VERCEL_TOKEN }}` once per project (`VERCEL_ORG_ID` and the project id as secrets), from a checkout of the same commit. Vercel builds remotely with its own encrypted environment, so server keys never reach the runner.
- `deploy-production` uses the GitHub environment `production` (no reviewers). Its URL output is the production URL.
- A manual production deploy from a laptop is not allowed. `CONTRIBUTING.md` says so.

## Security

- No secret is ever committed; gitleaks runs in the hook and over full history, and push protection is on.
- CI jobs get the least token permission they need. Third-party actions are pinned by SHA.
- Server keys exist only in Vercel's encrypted settings. CI builds use canary values, and the bundle scan proves they do not reach the browser.
- The production deploy builds on Vercel, not on the runner.
- `DEPENDABOT_READ_TOKEN` and `VERCEL_TOKEN` are repository secrets scoped to the `production` environment or to the jobs that need them.

## Decisions made here

1. **The "preview deploy" E2E gate runs in two parts.** A Vercel preview cannot reach a local chain, and running 40 money cases on Monad testnet on every push would burn faucet-limited AUSD and the 50 MON daily fee cap. So every push runs Tier 1 on a production build of the same commit in CI (Anvil), plus a no-transaction smoke set on the real Vercel preview. Tier 1 on Monad testnet runs by hand through `e2e-testnet.yml` before recording and at the final gate (PRD 14).
2. **Production deploys through the Vercel CLI from CI**, with the Vercel production branch pointed at a branch that never exists. This is the only way to make Vercel deploy production "only from a commit where all gates are green".
3. **CodeQL runs inside `ci.yml`**, not as a separate workflow, so `all-green` can depend on it.
4. **Low analysis findings are checked by machine** through `audits/accepted-findings.json` and SECURITY.md.
5. **AI skills are installed by a script that pins commits**, not by an unpinned plugin install.
6. **The server coverage floor (85% lines) also applies to `packages/shared`.**
7. **husky** is the hook manager; tool versions not managed by npm live in `tools/versions.env`.
