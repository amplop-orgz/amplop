# 16. Indexer

Status: Ready · Source: PRD sections 4 (R25–R27), 5, 6, 11, 13, 14, 16 · Depends on: 01, 02, 03, 04

## Goal

An Envio HyperIndex project in `indexer/` that turns every `AmplopEnvelopes` event into five entities (`Account`, `Deposit`, `Purchase`, `EmergencyRequest`, `Alert`) and serves them through one GraphQL address. The app uses it for Activity, envelope detail, move a purchase, the Emergency history and the parent's alerts. Balances, totals, schedules, the open Emergency request and card results never come from it, so the core flows work when it is down.

## In scope

- `indexer/config.yaml` for Monad testnet (chain 10143) and `indexer/config.e2e.yaml` for Anvil (chain 31337).
- `indexer/schema.graphql` with the five entities from PRD 11.
- One handler for each of the 22 events in 01 §3, including `TrustedRemoved` and `DaysSkipped`.
- Alert rules for R26 (except the low-envelope alert, which the app computes).
- The GraphQL query documents the app uses, in `packages/shared`.
- The rule the app uses to detect indexer lag.
- Hosting on Envio Cloud, and running locally for development and end-to-end tests.
- Handler unit tests with Envio's test helpers.
- The Envio bounty entry materials.

## Out of scope

- Screens that show activity and alerts (11, 14) and alert wording (14).
- The low-envelope alert: computed in the parent's app from contract totals (PRD 11, spec 14). It is never stored.
- Shop names, reasons and invite names: server only (R27, spec 05). The indexer never sees them.

Version and package.** Envio `envio@3.0.0-alpha.21` exactly (the version MONSKILLS `indexer` pins). `indexer/package.json`: name `@amplop/indexer`, `"type": "module"` (required by HyperIndex v3), `engines.node` `>=22.0.0`, scripts `codegen`, `dev`, `start`, `test`, `abi:sync`, `check`. ### Schema

**S16-7. Common fields.** Every entity that comes from an event stores where it came from:

| Field          | Type             | Meaning                                                                                         |
| -------------- | ---------------- | ----------------------------------------------------------------------------------------------- |
| `blockNumber`  | `Int!`           | `event.block.number`                                                                            |
| `logIndex`     | `Int!`           | `event.logIndex`                                                                                |
| `sortKey`      | `BigInt! @index` | `blockNumber × 100000 + logIndex`. One field to sort newest first across entities.              |
| `timestamp`    | `BigInt!`        | `event.block.timestamp` (real time)                                                             |
| `accountClock` | `BigInt!`        | `timestamp + Account.skipSeconds` at that event (01 §1). Screens show dates from this (PRD 12). |
| `txHash`       | `String!`        | `event.transaction.hash`, lowercase                                                             |

Entities updated by later events also keep the tx hash of each change (fields below). Addresses are stored lowercase. `bytes32` values are stored as lowercase `0x` hex strings. Token amounts are `BigInt` in token units (01 §8).

### Handlers

**S16-10. One handler per event.** Every event in 01 §3 has a handler in `indexer/src/handlers/`, registered with the v3 API (`indexer.onEvent({ contract: "AmplopEnvelopes", event: "<Name>" }, handler)`), grouped in files by entity: `account.ts`, `deposit.ts`, `purchase.ts`, `emergency.ts`, `changes.ts`. Shared helpers (`common.ts`) compute `sortKey`, `accountClock`, enum mapping and alert creation. Handlers that read an `Account` use `getOrThrow`: a missing account means `start_block` is wrong, and that must fail loudly at deploy, not be hidden.

| Event                   | Writes                                                                                                                                | Alert (S16-11)                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `AccountCreated`        | New `Account`: owner, split, `trusted = null`, `lockOn = true`, `skipSeconds = 0`                                                     | none                                       |
| `SplitSaved`            | If `immediate`: `Account.split = split`, pending fields null. Else: `pendingSplit`, `pendingSplitStartsAt`                            | `SplitSaved` when not `immediate`          |
| `InviteCreated`         | `Account.inviteKey`, `inviteExpiresAt`                                                                                                | none                                       |
| `TrustedLinked`         | `Account.trusted`, `trustedSince`                                                                                                     | none                                       |
| `TrustedRemovalStarted` | nothing else                                                                                                                          | `TrustedRemovalStarted`                    |
| `TrustedRemoved`        | `Account.trusted = null`; the open removal alert becomes `Done`                                                                       | none                                       |
| `Deposited`             | New `Deposit`                                                                                                                         | none                                       |
| `PurchaseApproved`      | New `Purchase`, status `Held`, `held = amount`                                                                                        | none                                       |
| `PurchaseDeclined`      | New `Purchase`, status `Declined`, `declineReason`, `held = 0`                                                                        | `PurchaseBlocked` when reason is `Blocked` |
| `PurchaseCollected`     | status `Collected`, `collected`, `returned`, `held = 0`, `collectedTx`                                                                | none                                       |
| `HoldReleased`          | status `Released`, `held = 0`, `releasedTx`                                                                                           | none                                       |
| `PurchaseRefunded`      | status `Refunded`, `refunded += amount`, `refundedTx`                                                                                 | none                                       |
| `PurchaseMoved`         | `envelope = to`, `moved = true`, `movedFrom`, `movedTo`, `movedTx`                                                                    | `PurchaseMoved`                            |
| `EmergencyRequested`    | New `EmergencyRequest`, status `Open`                                                                                                 | `EmergencyRequested`                       |
| `EmergencyOpened`       | status `Opened`, `openedBy`, `openedAmount`, `closedAt`, `closedTx`; open Emergency alert becomes `Done`                              | none                                       |
| `EmergencyCancelled`    | status `Cancelled`, `closedAt`, `closedTx`; open Emergency alert becomes `Cancelled`                                                  | none                                       |
| `LockOffStarted`        | nothing else                                                                                                                          | `LockOffStarted`                           |
| `LockOffDone`           | `Account.lockOn = false`; open lock-off alert becomes `Done`                                                                          | none                                       |
| `RecoveryApproved`      | nothing else                                                                                                                          | `RecoveryApproved`                         |
| `RecoveryDone`          | `Account.owner = newOwner`; open recovery alert becomes `Done`                                                                        | none                                       |
| `PendingCancelled`      | For `kind`: `Split` clears `pendingSplit*`; then the open alert of that kind (split, removal, lock-off, recovery) becomes `Cancelled` | none                                       |
| `DaysSkipped`           | `Account.skipSeconds = skipSeconds`                                                                                                   | none                                       |

**S16-11. Alert rules (R26).**

1. An alert is created only if `Account.trusted` is not null at that event. With no trusted person, nothing is stored and nothing fails (E8, R19).
2. `Alert.trusted` is the trusted address at that event. After a replacement, the old person's alerts stay theirs and the new person starts with none (B10, J6).
3. Kinds and their sources:

| R26 alert                                  | Event and condition                                                              | Kind                                                    |
| ------------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Emergency requested                        | `EmergencyRequested`                                                             | `EmergencyRequested`                                    |
| Blocked purchase declined (category only)  | `PurchaseDeclined` with `reason = Blocked`                                       | `PurchaseBlocked`                                       |
| A purchase moved (envelope names only)     | `PurchaseMoved`                                                                  | `PurchaseMoved`                                         |
| A rule change saved                        | `SplitSaved` with `immediate = false`; `LockOffStarted`; `TrustedRemovalStarted` | `SplitSaved`, `LockOffStarted`, `TrustedRemovalStarted` |
| A recovery asked                           | `RecoveryApproved`                                                               | `RecoveryApproved`                                      |
| An envelope under 20% of this week's share | not stored; spec 14 computes it from `totals()` and `envelopes()`                | none                                                    |

4. A second pending change of the same kind replaces the first (PRD 14 rule 7): when a new `SplitSaved` (not immediate) or `RecoveryApproved` arrives while an alert of that kind is `Active`, the old alert becomes `Replaced` and the new one is created. `Account.openAlert*` always points at the newest.
5. `PurchaseDeclined` with `NotEnough` never creates an alert.

### Queries the app uses

**S16-12. Query documents.** The app imports these from `@amplop/shared/indexer` (`packages/shared/src/indexer/queries.ts`), with hand-written result types next to each. The GraphQL dialect is the Hasura-style API Envio serves (`where`, `order_by`, `limit`, `_by_pk`; `BigInt` fields take `numeric` variables passed as decimal strings).

| Name                                                                               | Used by                                     | Shape                                                                                                                                                                                                                                              |
| ---------------------------------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ActivityQuery($accountId: numeric!, $limit: Int!)`                                | 2.9 Activity (11)                           | `Deposit`, `Purchase` and `EmergencyRequest`, each `where: { accountId: { _eq: $accountId } }`, `order_by: { sortKey: desc }`, `limit: $limit`. The app merges the three lists by `sortKey` descending and keeps the first `$limit`. Newest first. |
| `EnvelopePurchasesQuery($accountId: numeric!, $envelope: Envelope!, $limit: Int!)` | 2.3 Envelope detail (11)                    | `Purchase` where `accountId` and `envelope` match and `status` in `Held`, `Collected`, `Refunded`, newest first                                                                                                                                    |
| `PurchaseByIdQuery($id: String!)`                                                  | 2.10 Move a purchase (11)                   | `Purchase_by_pk(id: $id)`                                                                                                                                                                                                                          |
| `DepositByIdQuery($id: String!)`                                                   | 2.1 Allowance arrived history link (08, 11) | `Deposit_by_pk(id: $id)`                                                                                                                                                                                                                           |
| `EmergencyHistoryQuery($accountId: numeric!, $limit: Int!)`                        | 3.2 Waiting history (12)                    | `EmergencyRequest` for the account, newest first                                                                                                                                                                                                   |
| `AlertsForTrustedQuery($accountId: numeric!, $trusted: String!, $limit: Int!)`     | 1.1 Parent home (14)                        | `Alert` where `accountId = $accountId` and `trusted = $trusted` (lowercase), `order_by: { sortKey: desc }`, default `limit` 20                                                                                                                     |
| `AccountByOwnerQuery($owner: String!)`                                             | Diagnostics only                            | `Account` where `owner` matches. The app finds accounts with `accountOf` on the contract, not with this.                                                                                                                                           |
| `IndexerMetaQuery`                                                                 | Lag check (S16-14)                          | `_meta { chainId progressBlock sourceBlock isReady }`                                                                                                                                                                                              |

`AlertsForTrustedQuery` is always called with the `accountId` from the contract's `trustedAccountOf(address)` and the signed-in address. If the contract returns 0, the app makes no alert query (J6).

**S16-13. Client.** One small `fetch` wrapper in `apps/web/src/lib/client/indexer.ts` (owned by 06, as MONSKILLS `indexer` shows: POST JSON `{ query, variables }`, throw on `errors`). Timeout 4 s. No Apollo or urql.

### Core flows do not depend on it

**S16-14. Lag and outage rule.** Implemented in the app (06 provides the helper, 11 and 14 use it), defined here:

- What never reads the indexer: balances, totals, the release schedule, the open Emergency request, the result of a card payment, account lookup, trusted-person lookup (PRD 11). These come from the contract.
- The app calls `IndexerMetaQuery` and the chain head (`eth_blockNumber` through its normal RPC client) together, at most every 10 s while Activity, envelope detail, purchase detail or parent home is open.
- The indexer counts as **behind** when any of these is true: the request fails or takes more than 4 s; `isReady` is false; `head − progressBlock > INDEXER_MAX_LAG_BLOCKS` (30 blocks, about 12 s on Monad).
- When a screen just sent a transaction and knows its block number, the indexer also counts as behind for that screen until `progressBlock` is at or past that block.
- While behind, Activity shows "History is catching up" (PRD 5) and everything read from the contract still shows and works. The app never blocks a screen on an indexer call.
- When it catches up, the lists refresh without a reload (F11).

### Hosting

**S16-15. Envio Cloud (production).** The deployed app uses an Envio Cloud deployment. Steps, following MONSKILLS `indexer` "First deploy":

1. Prerequisites, done by the builder (never by an agent): `npm install -g envio-cloud`, `envio-cloud login`, the GitHub CLI `gh` installed and `gh auth login`. Envio Cloud deploys from GitHub and its CLI checks `gh auth status`; the MONSKILLS hook blocks `envio-cloud` commands until all four are in place.
2. `envio-cloud config set-org <org>`.
3. `envio-cloud indexer add --name amplop --repo <owner>/<repo> --branch main --root-dir ./indexer --config-file config.yaml --access-type public --dry-run`, check the output, then run it without `--dry-run`.
4. Wait for the first build (`envio-cloud deployment status amplop <commit>`, 5 s or more between polls).
5. Push one empty commit to trigger a rebuild (MONSKILLS: the first deployment sometimes never starts indexing). The message follows the commit rule: `chore(indexer): trigger envio cloud rebuild`.
6. Query `_meta` on the new deployment's endpoint (`envio-cloud deployment endpoint amplop <commit> <org> -q`). Healthy means `isReady: true` and `progressBlock` at or near `sourceBlock`. `eventsProcessed: 0` is not a failure.
7. `envio-cloud deployment promote amplop <commit>`.
8. Set `NEXT_PUBLIC_INDEXER_URL` to that endpoint in Vercel (Production and Preview), then run `ci.yml` by hand on `main` so `deploy-production` picks it up (02).
9. After every later promote, resolve the endpoint again and update Vercel only if it changed.
10. At the 18:00 13 Oct freeze, turn auto-deploy off (`envio-cloud indexer settings set … --auto-deploy false`, or the equivalent) so later documentation commits cannot replace the promoted deployment.

**S16-16. Local.** `npm run dev -w @amplop/indexer` runs `envio dev` against `config.yaml` (needs Docker; serves GraphQL on `http://localhost:8080/v1/graphql` by default). For Anvil, `npx envio --config config.e2e.yaml dev`. `envio dev -r` resets the database (v3 no longer resets by itself). 19 starts and stops the local indexer for the indexer-on and indexer-off groups; stopping must keep its database so a restart resumes and back-fills (F11).

**S16-17. Redeploy of the contract.** When 04 redeploys: update `deployments/monad-testnet.json`, run `npm run check -w @amplop/indexer` (fails until `config.yaml` matches), update `config.yaml` address and `start_block` in the same commit, wait for the new Envio Cloud deployment to sync, promote it, then do S16-15 steps 8 and 9.

**S16-18. Monorepo fallback.** On the first `indexer add --dry-run` and first build, confirm Envio Cloud installs dependencies from `--root-dir ./indexer` without its own lockfile. If it cannot, give `indexer/` its own `package-lock.json` (generated with `npm install --prefix indexer --workspaces=false`), remove `indexer` from the root `workspaces`, and add `npm ci --prefix indexer` to CI. This changes 01 §2 ("one committed lockfile"), so it is applied only if the check fails, and 01 §2 is updated in the same commit (see "Additions to 01 (status)", item 6).

## Errors and edge cases

| Case                                            | Behaviour                                                                                              |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Indexer down or slow                            | App shows "History is catching up"; core flows unaffected (S16-14, F10).                               |
| Indexer restarted after downtime                | Back-fills from its last block; Activity fills in, including what happened while it was off (F11).     |
| Event for an account the indexer never saw      | Handler throws (`getOrThrow`); deployment shows the error. Fix `start_block`.                          |
| Gambling decline with no trusted person         | Purchase row stored; no alert; no error (E8).                                                          |
| Trusted person replaced while a request is open | Old person's Emergency alert stays theirs; new person gets alerts only for later events (G14).         |
| Split saved twice during the wait               | First alert `Replaced`, second `Active` (H4).                                                          |
| Pending change cancelled                        | Its alert becomes `Cancelled` (B11, G17, H5, I3).                                                      |
| Recovery changes the owner                      | `Account.owner` updates; Activity keeps working because it is keyed by `accountId`, not by owner (I1). |
| Chain reorganisation                            | Envio's default `rollback_on_reorg: true` stays on.                                                    |
| Envio Cloud first deployment never starts       | Empty-commit rebuild (S16-15 step 5).                                                                  |

## Security

- The GraphQL endpoint is public and read-only. It holds only data that is already public on the chain (R27). It holds no shop name, reason, invite name or student name.
- `Alert` holds the category for blocked purchases and envelope names for moves, never a purchase id or amount, so the parent view built from it cannot list purchases (R25).
- The docs (18) say plainly that anyone can read purchase amounts, envelopes, times and kinds of shop from the contract or this endpoint (R27).
- The IP allowlist on Envio Cloud stays off: browsers on phones call the endpoint directly.
- No secrets in `config.yaml`; the RPC fallback is a public URL.

## Decisions made here

1. **Alert status.** Alerts carry `status` (`Active`, `Done`, `Cancelled`, `Replaced`) so the parent home can show that a request was opened or a change cancelled. PRD 11 does not say how alerts end.
2. **Alerts are addressed to the trusted person at the time of the event**, and queried with both `accountId` and `trusted`. A replaced trusted person sees nothing new; the new one sees nothing old.
3. **`sortKey`** (block × 100000 + log index) gives one newest-first order across `Deposit`, `Purchase` and `EmergencyRequest`, so Activity can merge three lists.
4. **`accountClock`** is stored on every row from `DaysSkipped`, so dates follow the account's clock (PRD 12) without a contract read per row.
5. **Weekly release rows are computed by the app** from `Deposit.parts` and `startDay`, since the contract emits no event for a release (releases are computed on read, PRD 7).
6. **Lag threshold:** 30 blocks or a 4 s timeout.
7. **Envio Cloud deploys from `main` with `--root-dir ./indexer`** (Envio's default branch is `envio`). The ABI is copied into `indexer/abis/` because the build may only see that folder.
8. **`AccountByOwnerQuery` exists but core code never uses it**; account lookup stays on the contract.
